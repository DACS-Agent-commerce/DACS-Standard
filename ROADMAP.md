# DACS Roadmap

DACS **v0.1** deliberately specifies only what is **shipped and reference-backed**:
a rail, method, or capability earns normative status when a live settlement /
verification path exists *and* a reference implementation exercises it. Everything
below is **anticipated follow-on work** — named honestly, with **no committed
dates**. DACS operates under progressive-anchoring phase PA-2 (single steward,
KyneSys Labs); we do not commit timelines we cannot guarantee.

This document is **informative**; the normative source is the
[specification](./spec/CORE.md). Where an item is already described in the
spec, the section is cited.

The roadmap has two parts:

- **Part 1 — Standard (normative).** Work that changes the *specification* itself —
  new rails, methods, rules, governance. These land in future minor versions
  (v0.2, v0.3, …) per the independent per-stage versioning in
  [CONTRIBUTING](./CONTRIBUTING.md), merge through the steward, and can affect
  conformance.
- **Part 2 — Ecosystem & tooling (non-normative).** Supporting artifacts *around*
  the standard — tooling, documentation, reference implementations, test vectors.
  These never change the spec or conformance, are welcomed as community
  contributions under a "contributor prototypes, steward owns the standard" model,
  and may be designated canonical by the steward if they prove solid.

# Part 1 — Standard (normative)

**Status legend.** **Shipped** — landed in v0.1. **Active** — being worked now (in development / in flight). **Candidate** / **Anticipated** / **Deferred** — queued, not yet started (a *Candidate* is scoped; *Anticipated* is directional; *Deferred* is explicitly out of v0.1). **Live** / **Partially live** — for shipped reference implementations / partially-deployed infrastructure. "design-issue first" means an RFC precedes any PR.

### Proposed rollout (planning milestones)

*Informative and non-binding. DACS versions **per stage** — a stage bumps its own minor when it gains a capability (DACS-4 is already v0.2 from SB-1..3) — so these waves are **planning milestones**, not global versions: each item carries its own stage's version when it lands. Sequenced by readiness + value + dependency; subject to change. (Part 2 ecosystem — SDK, tooling, docs, reference implementations — ships on its own non-normative track, outside these waves.)*

**Wave 1 — v0.2 milestone · harden the rails + fair reputation (contained, near-term):** session-bound settlement evidence (SB-1..3, #161) · ERC-4337 smart-account payers (#147 — absorbed into SB-3) · `pay-solana-spl` ATA-rent (#166) · blame-weighted completion + per-currency transaction-count (#31, #164) · `lei` registration-status → decision mapping (#146, gated on the PATH-OS↔DNO drift-test). *(Dropped as low-value: FX-normalised volume, ERC-8004 cross-claim hint, proactive rail-liveness probe (#23), and the modular ST-1..8 hoist — restructure declared complete (see Cross-substrate). Deferred to Wave 2: recovery-pending evidence (#25) and `cancelled` outcome (#92) — both evidence-shape / state-machine changes.)*

**Wave 2 — v0.3 milestone · bigger features (design-issue first):** native-DEM settlement rail (`pay-dem`, #168 — closes the no-native-rail gap; single-payee first) · `pay-evm-erc8183` escrow with delivery-gate (#8) · fee-split / multi-payee (#85 — revives as the `pay-dem` multi-payee follow-on) · HTLC anti-free-option (#24) · `FeeSchedule` disclosure · entitlement credential handover (#61) · private / access-controlled deliverables · liquidity-tank recovery-pending evidence (#25) · first-class `cancelled` outcome (#92) · abandoned-session terminal transition (#148) · canonical rating-`dimensions` namespace (#96) · `negotiate-multi-quote` · dynamic channel membership (#21) · sealed-envelope simultaneous-reveal · encrypted-to-parties anchoring (#68/#78) · verified-vs-controlled claim gate (#170 — v0.1 defect, Option 2 fix) + its DACS-1/DACS-2 control-boundary refactor (Option 1) · key delegation / authorized-key-set under a claim (compose vLEI/DID) · `ServiceCategory` vocabulary · DACS-X dispute (already parked here) · generic phase-hook · AML / Travel-Rule hook · per-artifact minor-version signalling (#79/#94 — reconsider; may be superseded by SIG-5).

**Wave 3 — v0.4+ / later · substrate, governance, live-path:** SR-3 / SR-4 wire harmonisation · PA-2 → PA-3 governance · selective / minimised-claim disclosure · streaming / subscription rails (#64) · L2PS key rotation / forward secrecy · CCI-keyed L2PS membership (substrate, in dev) · 6 new CCI contexts · DAHR validator-body-signed · `pay-d402` (the richer D402 micropayment protocol rail — distinct from the basic native-transfer `pay-dem`, which is pulled forward to Wave 2) · `pay-ap2` reference-backing · Liquidity Tank Phase 2–4.

| `FeeSchedule` disclosure in AgreementDocument | Candidate | Declared/negotiated fee disclosure for regulated contexts (EU MiCA, US MSB). Optional, non-breaking. Design-issue first. |
| Entitlement credential / token handover (#61) | Candidate | How an access **credential / token** is delivered to the grantee for a `deliver-entitlement` grant (vs. presenting the EntitlementRecord itself as the bearer proof). v0.1 adds the `serviceEndpoint` (*where* to access); the credential mechanism (*how to authenticate*) is an out-of-band auth concern left to a future version. |
| Private / access-controlled deliverables (`deliver-storage-program`) | Candidate; design-issue first | v0.1 `deliver-storage-program` anchors the payload via SR-2 at a **publicly-derivable address in cleartext** (`dacs4:deliverable:{jobId}`), so the deliverable is **world-readable** — correct for public deliverables, but it leaks a buyer's paid *private* content. Today's privacy paths are `deliver-entitlement` (serve from an access-controlled `serviceEndpoint`) or an access-controlled extended-pointer host. A first-class **private deliverable mode** should expose the substrate's native access control — **Demos Storage Programs support IAM / per-identity access control** — and/or an **encrypt-to-buyer** anchored mode, so the payload is readable only by the buyer/parties while its content hash stays public for tamper-evidence. Composes with the encrypted-to-parties anchoring item (#68/#78), which today scopes only the identity/vet/audit layer — extend it to cover DACS-4 deliverables. Also add a §9.6 disclosure that default `deliver-storage-program` is world-readable (mirroring the §7.5 public-anchor minimisation note). |
| Fee-split / multi-payee settlement model (#85) | Candidate; design-issue first | Settlement-time split of one price across distinct payees (e.g. seller + platform fee): `fees[]` / `splits[]` on the payment contract plus reconciliation, rounding, per-phase amount override, and volume attribution. v0.1's `PaymentPhaseInput.amount` is the single agreement price (PIPE-5 repetition settles the same amount), so fee-split is unrepresentable today. Distinct from the `FeeSchedule` *disclosure* candidate above — this is execution, that is declaration. |
| HTLC anti-free-option mechanism (#24, HTLC-10) | Candidate; design-issue first | Bonded premium / timeout fee / stake to compensate the payee for the inherent free option the preimage-holding payer holds in a basic HTLC swap (HTLC-10 discloses but does not remedy it). v0.1 steers option-sensitive flows to pay-cross-chain-liquidity-tank or a stake instead. |
| Session-bound settlement evidence on single-chain rails | Active (design note #159) | Bind a single-chain/provider settlement tx (`pay-evm-erc20`, `pay-solana-spl`, `pay-ap2`, `pay-x402`) to its `jobId` so a SettlementEvidence record cannot cite a tx from another session or a coincidental transfer of the right amount to the payee. HTLC already binds via the jobId-derived preimage (HTLC-5); the single-chain rails have no equivalent. **Design note #159** frames the two threats (coincidental-citation vs cross-session double-count) and three options: a `jobId` memo / log-emitting forwarder on EVM (and binding `jobId` into the x402 EIP-3009/Permit2 authorization), an SPL memo, or a normative consumer-side tx-hash-uniqueness-per-jobId check — leaning to a universal uniqueness backstop + an optional per-rail on-chain marker. Closes a cross-session replay / double-count gap on the most-used rails (Round-3 review); overlaps #147 (4337 payers). Targets DACS-4 v0.2. |
| ERC-4337 smart-account payers on `pay-x402` | Candidate; design-issue first | Support a buyer paying from an **ERC-4337 smart-contract account** (account abstraction), not only an EOA. The `pay-x402` verifier today implicitly assumes an EOA authorization (the reference path signs EIP-3009/Permit2); a smart account approves via **ERC-1271** (`isValidSignature`), so a 4337 payer is rejected as written. Two additive, backwards-compatible changes: **(1)** the x402 payment-authorization check MUST accept ERC-1271 contract signatures for contract-account payers (select by whether the payer address has code), alongside the EOA path; **(2)** bind settlement evidence via the ERC-20 `Transfer(from=payerAccount, …)` event + `jobId`, **not** `tx.from` — because a 4337 tx is submitted by the EntryPoint/bundler, not the payer (this overlaps the "Session-bound settlement evidence" row above, which a 4337 payer forces from optional to required). Out of scope: the 4337 machinery itself (UserOperation / bundler / EntryPoint / paymaster) stays payer-wallet/infra; identity is unaffected (a smart-account address is just a `cci-xm:evm:…` claim). Scoped to `pay-x402` (and any `pay-evm-erc20` flow that verifies an off-chain authorization). |
| Cross-currency refunds (AMEND-3) | **Parked / backlog — no driver** | Allow a refund in a different currency than the settlement (e.g. an AP2 fiat payment refunded as USDC). v0.1 requires same-currency refunds because the AMEND-3 over-refund bound is not evaluable across currencies; a future version would add an **FX-reference** to the amendment so the bound converts (`sum(convert(refundAmount, fxRef)) ≤ paymentAmount`). **Parked 2026-06:** no concrete cross-currency-refund use case yet, and it introduces the same FX-machinery dependency we declined for the FX-normalised volume aggregate (#164). **Revisit on demand** (e.g. real AP2-fiat-paid / crypto-refunded flows). Likely lean when revived: a **party-cited** FX reference (no live oracle) — since AMEND-3 only guards against *over*-refund, a gamed rate can't exceed the paid value, and an unfair rate is a DACS-X dispute concern, not an over-refund one. |
| `pay-solana-spl` payee-ATA rent handling | Candidate | Specify who funds the rent-exempt reserve when the payee's SPL associated-token-account must be created, a `createPayeeAtaIfMissing` rail param, and the error class when ATA creation fails for payer SOL shortfall. v0.1 leaves the rent-payer and create-failure path unspecified (Round-3 review). |

| Verified-vs-controlled claim gate (#170) | **v0.1 defect** · Option 2 (near-term) | §6.3.2's verification-resolution rule gates on `decision == pass` + identifier-match with **no control / holder-binding requirement**, and `VerifyResult` records no control indicator — so a **validity-only** (bare-registry, e.g. `lei` GLEIF lookup) `pass` is indistinguishable from a **control-establishing** (holder-bound vLEI / cci-xm / sign-with-key) one and qualifies as a *controlled* `presentedBy` / reputation key. Heavier than Option 2 (a v0.3 identity-model boundary change); Option 2 closes the defect without it. |
| Key delegation / authorized-key-set under a primary claim | Anticipated; design-issue first · **compose, don't reinvent** | A primary claim — especially an entity claim (**one LEI, many agent keys**) — has no explicit, per-key authorized set: v0.1 cannot express "these keys may act as `lei:5493…`", nor revoke one compromised agent key without burning the whole claim. The questions: a claim → authorized-key-set binding, per-key authorization **and revocation**, and the root-of-trust (who signs the roster). **Decision lean: compose existing delegation standards — vLEI (GLEIF KERI entity→agent delegation chains) and W3C DID verification-method sets / key rotation — rather than build a DACS-native delegation primitive** (DACS ethos: claims-not-roots, compose open standards). A minimal native delegation may still be warranted only for self-sovereign `key:` / `cci-xm:` identities that have no external credential standard. Relates to #170 and the control-boundary refactor: a holder-bound credential carries the delegation / authorized-key story intrinsically, so **requiring one (the #170 Option-2 fix) is the near-term partial answer** to "which keys legitimately act under this claim". This is also the proper home for the genuine residual of "primary-claim revocation" — per-key, not per-claim. |
| Selective / minimised-claim disclosure | Anticipated | v0.1 provides no per-claim selective disclosure at the bundle layer (§11.2.7; scope note §6.3.2). |
| Encrypted-to-parties anchoring for the identity/vet/audit layer (#68, #78) | Candidate; design-issue first | An `encrypted-anchored` mode (mirroring §8.7's transcript machinery) for AttestationBundles, commit-agreement records, and DACS-2 VerifyResults — encrypt the record to the session parties while keeping the content hash public for tamper-evidence, plus optional **hashed anchor addresses** (`H(jobId‖scheme‖identifier)`) so the address stops enumerating who-screened-whom. ## Verify & accountability (DACS-5)

| Item | Status | Notes |
|------|--------|-------|
| DACS-X (dispute / execution-verification) | Deferred — v0.3 | Dispute initiation, arbitrator credentialing via DACS-1/2, named-arbitrator transcript disclosure (§8.7, already specced), superseding outcome bundles (§11.2.1). The accountability layer — makes the session record adjudicable; it does not hide session content. **Parked to v0.3 (steward decision, 2026-06).** Rationale: the v1 remedy is *advisory* (a reputation reweight, not on-chain enforcement), so it has teeth only for expensive/institutional identities — a cheap-identity loser simply re-keys (§10.5 no-cross-lifting) — and there is no arbitrator market or dispute volume yet, so a normative chapter now is premature (YAGNI). It stays strategically important for **institutional / regulated / real-money** commerce, where recourse is table-stakes; **revisit on a demand signal** (an adopter/regulator-facing use case or real dispute volume). Meanwhile the design + prototype mature **non-normatively** via PATH-OS's prototype + the #99 vector loop, so it's draftable when demand arrives. **Design rationale banked:** it's a **cross-cutting standard** (not a 6th stage — reactive, three-party, consumes all five stages), with a **narrow seam to DACS-5** (a distinct arbitrator-signed `DisputeOutcome` → reputation reweight, not a three-sided bundle); contract-account (ERC-4337) signers are handled at the signature layer (#147), not in DACS-X; **enforcement** of a remedy is the `pay-evm-erc8183` escrow rail (the *proactive* half — holding payment until delivery is confirmed), **not** DACS-X. v0.1 has neither half (settlement is evidence-based, not escrow-gated, §9.9). |
| Transaction-count metric (#31) | Active (DACS-5 v0.2, #164) | A per-currency transaction count on `observedTransactionalVolume`, strengthening the anti-collusion "few large vs many tiny" heuristic (§10.11); shipping as `transactionCountByCurrency` in #164. The **FX-normalised aggregate** half was **dropped** — it polishes a signal the spec already calls weak and would need an FX-oracle; reconsider only on real cross-currency-comparability demand. |
| First-class `cancelled` outcome (#92) | Candidate; design-issue first | A reputation-neutral `cancelled` / `cancelled-with-fee` SessionState + AttestationBundle outcome that honours a pre-agreed `cancellationPolicy` without it reading as an `aborted-by-self` fault. v0.1 makes `cancellationPolicy` informational-only; this wires it through the §10.3.1 state machine and excludes it from the §10.5 fault denominator. A genuine fairness gap (a legitimate policy-cancellation currently reads as the canceller's fault) — but it is a **state-machine change**, so design-first. (Blame-weighted completion, #164, already fixes the *counterparty*-cancel side; this is the *self*-cancel-per-policy side.) Composes with the ST-3 "withdrawal is a right" framing. |
| Abandoned-session terminal transition (#148) | Candidate; design-issue first | §10.3.1 has **no timeout/expiry exit** from a `*-pending` state and no `expired` terminal — a party who simply vanishes (never responds, never aborts) leaves the session stuck in `*-pending` indefinitely, never reaching a terminal state and so never producing a bundle (ST-6). Add either a new `expired` terminal + a timeout transition from any `*-pending` state, or an `aborted-by-*` outcome with a timeout trigger. Interacts with bundle production (ST-6), reputation (does an abandoned session count against a party?), and the per-listing timeout source — hence design-issue first. Surfaced by the D9/SN-4 review (#143): v0.1's backstop is the verifier-side **bounded challenge lifetime** (CORE §B.8 SN-4), which bounds nonce state but does not give the session itself a terminal state. |
| Canonical rating-`dimensions` namespace (#96) | Candidate; reconsider on demand | A registered set of per-dimension rating keys (timeliness, communication, …) with a normative value range and a per-dimension `ReputationDerivation` metric, making dimension-level reputation a comparable cross-impl signal. v0.1 treats `dimensions` as opaque pass-through (RT rules, §10.6). The carrier field already shipped, so implementations can experiment; standardising the *vocabulary* before real usage shows which dimensions matter is premature (same "let it emerge first" logic as ServiceCategory) — revisit once the opaque field sees real use. |
| Blame-weighted completion metric | Active (DACS-5 v0.2, #164) | A completion metric that does not penalise a party for counterparty-caused non-completions, closing the griefing residual v0.1's `completionRate` leaves (a counterparty repeatedly opening-and-aborting depresses the target's rate). Shipping as the additive `counterpartyAdjustedCompletionRate` in #164 (`completionRate` unchanged). |

## Cross-substrate & governance

| Item | Status | Notes |
|------|--------|-------|
| Modular restructure — Core + stage modules + Primer (v0.2 format) | Landed — complete | Re-packaged the single specification into a non-normative **Primer**, a **CORE** (shared types, canonical form, signatures, substrate requirements, governance), five self-contained **stage modules** (DACS-1…DACS-5), and companion references. **No normative rule-text change.** The genuinely shared cross-cutting primitives are hoisted into CORE — CF-1..CF-4, CD-1, the §B.7 signature scheme, §B.8 session-nonce. **Decision: the session state machine (ST-1…ST-8) stays in DACS-5** — it is the DACS-5 session-lifecycle model (the bulk of its references, and the state→outcome map feeding reputation, are in DACS-5), referenced by DACS-4 as a normal cross-module citation; hoisting it would churn ~68 citations for zero capability and put a DACS-5-centric concept in CORE. The "used across modules → Core" test is a heuristic for *shared foundations*, not a mandate for every cross-referenced concept. Restructure is therefore complete. |
| SR-3 / SR-4 wire-protocol harmonisation | Anticipated (v2) | v0.1 specifies SR-3 and SR-4 at the trust-property level only; cross-substrate sessions cannot complete for SR-3- or SR-4-dependent phases until wire formats are aligned (§5). |
| PA-2 → PA-3 multi-party governance | Anticipated | Constitution of a multi-party steward body to replace the single-signer recipe and rail registries (§11.2.6). |
| Generic phase-hook interface (à la ERC-8183 `IACPHook`) | Candidate; design-issue first | A normative pre/post-phase hook surface — `beforePhase` / `afterPhase(phaseSelector, data)` — letting integrators inject custom logic (allowlists, fee splits, reputation gating, compliance/KYC checks, bidding) at any pipeline phase **without** defining a new phase type. Mirrors ERC-8183's stable `before/after(selector)` extension model, with the same safety discipline (refund / terminal / abort / substrate-recovery paths non-hookable so recovery can't be blocked; gas-bounded; hook fixed at session start). Gives DACS 8183-style drop-in extensibility within the richer Identify→Vet→Negotiate→Settle→Verify lifecycle, rather than only the structured phase-type / recipe / rail extension points it has today. |

Pairs with the §11.2.5 cross-version work. |
| AML / Travel-Rule compliance-metadata hook | Candidate; design-issue first | An optional extension point carrying compliance metadata (e.g. a Travel-Rule flag) for flows that touch real money (fiat via AP2, stablecoins), so DACS is usable in regulated markets. # Part 2 — Ecosystem & tooling (non-normative)

Builder-facing artifacts *around* the standard. None change the spec or conformance.
Welcomed as community contributions under the "contributor prototypes, steward owns
the standard" model; if an artifact proves solid the steward may designate it
canonical. Anything that **mirrors** the spec (a reference tool, a generated doc)
MUST generate from this repo — so it cannot drift from the source of truth — and
version-stamp which DACS version it reflects.
