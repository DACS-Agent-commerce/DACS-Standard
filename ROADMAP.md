# DACS Roadmap

DACS **v0.1** deliberately specifies only what is **shipped and reference-backed**:
a rail, method, or capability earns normative status when a live settlement /
verification path exists *and* a reference implementation exercises it. Everything
below is **anticipated follow-on work** — named honestly, with **no committed
dates**. DACS operates under progressive-anchoring phase PA-2 (single steward,
KyneSys Labs); we do not commit timelines we cannot guarantee.

This document is **informative**; the normative source is the
[specification](./spec/CORE.md). Where an item is already described in the
spec, the section is cited.

The roadmap has two parts:

- **Part 1 — Standard (normative).** Work that changes the *specification* itself —
  new rails, methods, rules, governance. These land in future minor versions
  (v0.2, v0.3, …) per the independent per-stage versioning in
  [CONTRIBUTING](./CONTRIBUTING.md), merge through the steward, and can affect
  conformance.
- **Part 2 — Ecosystem & tooling (non-normative).** Supporting artifacts *around*
  the standard — tooling, documentation, reference implementations, test vectors.
  These never change the spec or conformance, are welcomed as community
  contributions under a "contributor prototypes, steward owns the standard" model,
  and may be designated canonical by the steward if they prove solid.

---

# Part 1 — Standard (normative)

**Status legend.** **Shipped** — landed in v0.1. **Active** — being worked now (in development / in flight). **Candidate** / **Anticipated** / **Deferred** — queued, not yet started (a *Candidate* is scoped; *Anticipated* is directional; *Deferred* is explicitly out of v0.1). **Live** / **Partially live** — for shipped reference implementations / partially-deployed infrastructure. "design-issue first" means an RFC precedes any PR.

### Proposed rollout (planning milestones)

*Informative and non-binding. DACS versions **per stage** — a stage bumps its own minor when it gains a capability (DACS-4 is already v0.2 from SB-1..3) — so these waves are **planning milestones**, not global versions: each item carries its own stage's version when it lands. Sequenced by readiness + value + dependency; subject to change. (Part 2 ecosystem — SDK, tooling, docs, reference implementations — ships on its own non-normative track, outside these waves.)*

**Wave 1 — v0.2 milestone · harden the rails + fair reputation — released in v0.2:** session-bound settlement evidence (SB-1..3, #161) · ERC-4337 smart-account payers (#147 — absorbed into SB-3) · `pay-solana-spl` ATA-rent (#166) · blame-weighted completion + per-currency transaction-count (#31, #164) · `lei` registration-status → decision mapping (#146). *(Dropped as low-value: FX-normalised volume, ERC-8004 cross-claim hint, proactive rail-liveness probe (#23), and the modular ST-1..8 hoist — restructure declared complete (see Cross-substrate). The two items originally deferred to Wave 2 — recovery-pending evidence (#25) and the `cancelled` outcome (#92, shipped as ST-10) — were pulled into the v0.2 cut alongside the abandoned-session timeout (#148, ST-9) and the minor-version additivity contract (#79/#94).)*

**Wave 2 — v0.3 milestone · design-issue-first (the set that survived design review; released in v0.3, 2026-07-03):** `FeeSchedule` disclosure (#186 — disclosure-only; reconciliation scoped to the network fee, non-gating; shipped #199) · private / access-controlled deliverables (#190 — `buyer-only` via the existing Demos storage-program ACL + portable `encrypt-to-buyer`; pure spec, no substrate work; shipped #201). *(Reviewed out of the Wave-2 set 2026-06, dispositions in the Parked / backlog table: `negotiate-multi-quote` #189 parked — redundant with separate fixed-price listings, no driver; AML / Travel-Rule hook #191 parked — no driver, and a thin hook cannot confer regulator compliance; key delegation #188 parked — held for the CCI-native form, behind the CCI-keying substrate work; fee-split / multi-payee #85 parked — blocked on DemosWork rollback-atomicity. Moved to Wave 3: sealed-envelope simultaneous-reveal #192. Landed early in the v0.2 cut: `pay-dem` #168, recovery-pending evidence #25, `cancelled`/ST-10 #92, timeout/ST-9 #148, additivity contract #79/#94. Resolved separately: HTLC anti-free-option #24, entitlement handover #61, encrypted-to-parties anchoring #68/#78.)*

**Wave 3 — v0.4+ / later · substrate, governance, live-path:** SR-3 / SR-4 wire harmonisation · sealed-envelope simultaneous-reveal (#192 — cryptographic commit-to-all-then-reveal so a non-neutral orchestrator can't learn interim bids before the reveal window closes; the primitive (timelock-against-a-beacon target / committee fallback) wants the SR-3/SR-4 substrate work, but a **primitive-independent conformance invariant + two vectors are designable earlier**, addressing the §8.12 reveal-manipulation residual before the impl) · selective / minimised-claim disclosure · streaming / subscription rails (#64) · CCI-keyed L2PS membership (substrate, in dev) · 6 new CCI contexts · DAHR validator-body-signed · `pay-d402` (the richer D402 micropayment protocol rail — distinct from the basic native-transfer `pay-dem`) · provider-rail reversal / chargeback semantics (#220) · Liquidity Tank Phase 2–4. *Completed on this track: `pay-ap2` reference-backing (#221) now has an official-AP2-verified SDK path, a network-exercised Stripe-test/DAHR/Demos run, durable replay protection, and a public conformance fixture; production rail availability remains operator-gated.*

| Item | Status | Notes |

| Transaction-count metric (#31) | Landed (v0.2 — #164) | A per-currency transaction count on `observedTransactionalVolume`, strengthening the anti-collusion "few large vs many tiny" heuristic (§10.11); shipping as `transactionCountByCurrency` in #164. | First-class `cancelled` outcome (#92) | Landed (v0.2 as ST-10 — #183) | A reputation-neutral `cancelled` / `cancelled-with-fee` SessionState + AttestationBundle outcome that honours a pre-agreed `cancellationPolicy` without it reading as an `aborted-by-self` fault. v0.1 makes `cancellationPolicy` informational-only; this wires it through the §10.3.1 state machine and excludes it from the §10.5 fault denominator. | Abandoned-session terminal transition (#148) | Landed (v0.2 as ST-9 — #182) | §10.3.1 has **no timeout/expiry exit** from a `*-pending` state and no `expired` terminal — a party who simply vanishes (never responds, never aborts) leaves the session stuck in `*-pending` indefinitely, never reaching a terminal state and so never producing a bundle (ST-6). Add either a new `expired` terminal + a timeout transition from any `*-pending` state, or an `aborted-by-*` outcome with a timeout trigger. Interacts with bundle production (ST-6), reputation (does an abandoned session count against a party?), and the per-listing timeout source — hence design-issue first. Surfaced by the D9/SN-4 review (#143): v0.1's backstop is the verifier-side **bounded challenge lifetime** (CORE §B.8 SN-4), which bounds nonce state but does not give the session itself a terminal state. |
| Blame-weighted completion metric | Landed (v0.2 — #164) | A completion metric that does not penalise a party for counterparty-caused non-completions, closing the griefing residual v0.1's `completionRate` leaves (a counterparty repeatedly opening-and-aborting depresses the target's rate). Shipping as the additive `counterpartyAdjustedCompletionRate` in #164 (`completionRate` unchanged). |
| SR-2-anchor-timestamp windowing (§10.5.1 SHOULD) | **Deferred — reference fails closed** | §10.5.1 (spec :832/:1010) **lets** high-stakes consumers window a reputation derivation against the substrate's SR-2 anchor timestamp rather than the producer-set `finalisedAt` — a **SHOULD**, not a MUST-implement (the normative `derive()` algorithm windows on `finalisedAt`, spec :604). The reference implements only `finalisedAt`: `windowingBasis` is now REQUIRED + vocabulary-checked `{finalisedAt, sr2-anchor-timestamp}`, and a declared `sr2-anchor-timestamp` **fails closed** — `derive()` refuses it and `replay_receipt` refuses an `sr2`-declared receipt with a distinct not-implemented reason (PR #248 round-13) — rather than recording `sr2` while silently windowing on `finalisedAt`. **Deferred to implementation:** windowing against the SR-2 anchor timestamp, plus the differential two-clock regression (two bundles falling on opposite sides of the two clocks selecting different sets). Revisit when the reference input model can supply the anchor timestamp. |

Latent only because v0.1 is the first version; **activates at v0.2**. **Fix is a clarification, NOT the originally-proposed `producedUnder` minor-version field:** pin the **additivity contract** (a minor adds optional fields only; anything an older reader must *act on* — a new enum value / phase type — requires a **major** bump), point §11.2.5 forward-compat explicitly at **SIG-5 preserve-unknown** (which already covers additive skew both directions), and state §6.3.4 step (2) gates on **major** mismatch. # Part 2 — Ecosystem & tooling (non-normative)

Builder-facing artifacts *around* the standard. None change the spec or conformance.
Welcomed as community contributions under the "contributor prototypes, steward owns
the standard" model; if an artifact proves solid the steward may designate it
canonical. Anything that **mirrors** the spec (a reference tool, a generated doc)
MUST generate from this repo — so it cannot drift from the source of truth — and
version-stamp which DACS version it reflects.
